## 2026-09-20: Correct macOS Memory Accounting

The initial RSS/unused-page footer was technically labeled but misleading for
practical memory monitoring. The live Kidi process had a 6.241 GiB footprint
while RSS was only 0.307 GiB after compression; `top` showed about 6391 MiB.
At the initial observation macOS had only 76 MiB unused, but `memory_pressure -Q`
reported 44% system-wide free. These are different counters, not a unit error.

The macOS footer now uses `TASK_VM_INFO.phys_footprint` and labels the kernel
`kern.memorystatus_level` percentage as RAM headroom. It does not convert that
percentage into a purported free-byte budget. An independent live-process check
matched 2.81 GiB displayed to 2.807 GiB from `proc_pid_rusage`; both the footer and
`memory_pressure -Q` reported 31% in that check. The user's running chat was not
stopped or restarted. Values are snapshots and change with other workloads.

The existing live-terminal regression now compares the displayed footprint with
`proc_pid_rusage` for the still-running child process, not just a plausible range.
Native CPU and rebuilt-wheel Metal CLI tests pass; the CLI and wheel are rebuilt.
Test processes used zero retained expanded-weight cache to reduce pressure while
the user's chat remained open. This does not change the default cache policy.

### Device State and Replay Probe

Experimental recurrent decode now keeps the selected token and position in
persistent device buffers, generates causal/window masks on Metal, gathers
host-equivalent rotary values from cached device tables, and uses device-indexed
single-token K/V writes. Default prefill still uses contiguous range writes.
Fixtures pass on both paths; an exploratory real-model run matched all tokens
and reached 84.17 decode tokens/s. Paired combined-path validation is pending.

The installed SDK supports indirect compute command buffers, but MPSGraph may
commit its underlying command buffer while encoding. A two-projection packed
kernel replay probe therefore tests only the native-kernel portion. It preserves
exact Q2/Q4/Q8 outputs with dependencies and changed input contents. Encoding
savings were below one microsecond per pair; GPU timings were mixed. No full-step
replay or production speedup is claimed. `kidi_metal_packed_bench replay` reproduces
the probe; broader replay requires a supported way to integrate the remaining
MPSGraph operations or replace measured blockers with direct kernels.

### Rejected Integer GEMV

A trained-A8/packed-Q2/Q4/Q8 integer-accumulation candidate passed the tiny tests
but lost on the full model. Three paired processes per prompt measured about
70 versus 82 decode tokens/s short, 64 versus 73 long. The 29-position independent
probe gave 27/29 top-1 and KL 0.04447 versus the earlier floating path's 29/29 and
0.03653. The candidate and its environment switch were removed, not promoted or
kept as a slower optional path. No numerical tolerance was loosened. The next
projection investigation targets native matrix execution rather than assuming
integer arithmetic is faster on this GPU.

### Rejected Cooperative Tensor Prototype

An original FP16 cooperative-tensor matmul using Metal Performance Primitives
matched MPSGraph outputs exactly on the tested tails and projection shapes.
Runtime API constraints differed from SDK examples (single SIMD group, no
`get_mask`, output columns limited to 16/32). With the supported 16x32 tile
and unrolled register loops, production shapes still took 557/2130/5023 us
versus MPSGraph 345/736/1822 us. The standalone probe was removed from runtime
code; MPSGraph remains the prefill matrix implementation. This rejects this
prototype, not the entire M5 tensor approach. Next: calibrated output epilogues
around the proven matrix implementation, plus measured attention work.

### Calibrated Epilogue Trial: Not Promoted

Putting output calibration into the MPSGraph matmul raised long-prompt/chunk-512
prefill from roughly 1770 to 1920 tokens/s in three alternating process pairs.
Ties-to-even/clipping fixtures passed, but full-model generated tokens differed.
The independent 128-position probe retained 123/128 top-1 yet changed KL from
0.0130452 to 0.0136609 and NLL delta from -0.0096231 to +0.0068820. Thus small
fixtures are insufficient to prove fused FP16 intermediate semantics. The path
was removed after a second variant (explicit FP16 graph output followed by a
cast-and-round kernel) also failed the existing Gemma tolerance. Both trial flags
were removed. MPSGraph may choose different accumulation/intermediate behavior
when output graphs change; the tiny boundary fixture alone did not establish
equivalence. Neither variant is an accepted speed result.

### Norm/Rotary Fusion and Native Attention

Direct Metal RMS normalization plus RoPE fusion passed width-40/256/512,
batch/head, and Gemma fixtures. Three paired short-prompt processes improved
decode from about 83.2 to 84.0 tokens/s; the independent 29-position logits
metrics are unchanged. `KIDI_SEPARATE_RMS_ROTARY=1` retains the comparison path.
This is a small dispatch reduction, not a parity claim.

Native MPSGraph scaled-dot-product attention passed tiny tests but did not help
prefill and reduced long-prompt decode from roughly 75 to 66 tokens/s. Independent
prefill top-1 changed from 123/128 to 122/128. The candidate was removed. Faster
attention still requires a measured kernel/layout improvement; a fused API name
does not guarantee a faster implementation for these shapes.

Flattening the calibrated projection's leading dimensions to a 2D matrix also
preserved the independent prefill metrics, but reached only about 1645 tokens/s
on the long/chunk-512 trial versus the recent composed path near 1770. It was
removed. The next investigation moves to CPU operator execution and remains
separate from GPU speculation; repeated graph-layout changes without a measured
kernel benefit are not productive.

## CPU Prefill Single-group Specialization

The QAT path uses one trained weight-scale group per output channel. A direct
integer dot followed by weight-scale then activation-scale multiplication avoids
the generic blockwise split/transpose/reduction structure for this case.

The initial all-row trial had inconsistent decode results, so it was restricted
to multirow prefill. Five alternating process pairs (1024 prompt, 16 recurrent
tokens, 2 warmups, 3 measurements) all improved prefill: 456.8/478.2,
438.7/463.1, 433.8/447.2, 426.9/446.7, 430.7/444.4 tokens/s before/after.
All 15 candidate sequences match; preparation remains zero. The independent
128-position CPU metrics are unchanged (125/128, KL 0.0138114).

This specialization is enabled only for trained-static, single-group, multirow
packed projections. Single-token decode and general grouped/PTQ behavior remain
unchanged. `KIDI_CPU_BLOCKWISE_PREFILL=1` restores the generic path. This is a
3-6% measured prefill gain, not CPU parity with LiteRT-LM.

## Prefix Reuse Foundation: Opt-in Dense Snapshot

`Gemma4::fork_state` validates and copies only the completed prefix into an
independent state. Shared-K/V consumers still refer to their producing layers;
tests verify exact resumed logits and source-cache isolation on both backends.

`--prefix-cache-bytes N` enables one exact-token prefix entry per generator,
bounded by its K/V tensor bytes. Matching is restricted to completed prefill
chunks and always leaves input to execute for the next logits. Chunk and attention
policy changes invalidate the entry; disabling or shrinking the budget evicts it.
The cache cannot cross model instances. Reuse counters are emitted explicitly.

A first real-model smoke test reused 896/1024 prompt tokens and produced exact
outputs on CPU and GPU. This is a cache-hit result, not faster uncached inference.
The current implementation copies dense K/V on resume, is not paged/zero-copy,
and its byte budget excludes transient/native-library allocations. This is a
correctness foundation for subsequent block sharing, not the final serving cache.

## Zero-copy K/V Prefix Views

Gemma materialized K/V prefix slices before attention. The first attempt passed
full-capacity storage directly, allowing attention to crop internally. It improved
long decode in three pairs (CPU roughly 40-42 to 46-49 tokens/s; GPU 74 to 77),
but GPU generated tokens diverged at token 3. CPU output was exact. Thus the
full-capacity binding was not accepted as a copy-only optimization.

Course correction: select the single cache batch, narrow its contiguous row
prefix, and reshape the view back to the original attention dimensions. This
removes the copies while preserving MPSGraph's previous input shapes and CPU
scheduling. The focused Gemma tests pass; a real long-prompt GPU check now matches
all baseline token IDs and reaches about 82.2 decode tokens/s with zero warm
preparation. Fresh paired validation of the corrected version is in progress.

Five fresh paired processes on each backend now confirm exact tokens for all
30 measured candidate requests and zero warm preparation. Long-context decode
improved in every pair: CPU 12-16%, GPU 9-10%. Prefill was largely unchanged;
one CPU pair regressed during rate drift. The retained implementation is the
shape-preserving view, not full-capacity binding. Raw records are in
[cache-view-results.json](cache-view-results.json).

## Gate Fusion and Decode Attention Probe

GELU plus multiply now shares a Metal pointwise dispatch in the MLP and PLE
gates. Three alternating short-prompt pairs reduced request latency from
836.1/835.8/838.9 to 827.9/829.7/828.3 ms. Saturation/tail checks and model
fixtures pass; independent decode metrics remain 29/29 top-1 and KL 0.0365263.
`KIDI_SEPARATE_GELU_MULTIPLY=1` restores the comparison path.

A bounded single-query attention kernel (no split/merge, FP32 accumulation)
passed the tiny oracle but ran at only 32.9 long-context decode tokens/s and
changed generated outputs; the independent small probe was 28/29. It was removed.
This rejects that untuned kernel, not paged attention or a future tiled design.

## Paged Ownership Foundation

Added a byte-budgeted K/V page pool with heterogeneous producer widths, move-only
leases, sealed complete-page sharing, writable clones, and queued-use retention.
Pages released by requests cannot be reassigned until the pool's owning context
has completed those uses. Tests exercise queued CPU/Metal writes, sharing,
clone isolation, exhaustion, reclamation and uninitialized-prefix rejection.

The opt-in one-entry prefix cache now stores completed chunks as immutable pages
in that model-owned pool. Request restore still copies into dense K/V; this is
**page-backed prefix storage, not paged attention or continuous batching**.
Existing exact-output hit/miss, changed-suffix, budget-shrink/disable and policy
invalidation regressions pass on CPU, Metal, and experimental device-state Metal.
`prefix_reserved_bytes` reports allocated pool storage separately from occupied
`prefix_cache_bytes`. Zero budget allocates no page pool. Page lifetime is tied
to one context/model; a saved block-table tensor is only valid while its page
leases remain owned or retained through the submitted work.

## Packed Multi-request Decode: In Progress

The shared Gemma layer equations now accept independent cache segments. Projections
and pointwise work operate on packed request rows, while attention retains each
request's own length, position, mask and cache. Model tests compare batches of
2/4 against serial logits, including reordered/retired rows and alias rejection.
Batch-four QAT initially selected the FP16 prefill path; an explicit scoped decode
policy now preserves FP32 packed-vector arithmetic instead of relaxing tolerances.

A real-checkpoint forced-token probe compared 32 positions with zero logit error
on both backends. Four tokens took 39.65 ms batched versus 66.01 ms serial on CPU,
and 34.06 versus 45.34 ms on GPU in one process. These are inner-step exploratory
numbers, not batch-one or serving throughput claims.

`Generator::generate_batch` now supports 1-16 prompts with independent prefills and
active-row decode retirement through the existing decoder's EOS/length rules.
It explicitly rejects prefix-cache options for now. Four complete real generations
match serial outputs and stop lengths on CPU and GPU. However repeated mixed
prompt/batch shapes exceed the current prepared-cache working set: third-run
preparation remained about 2.8 s CPU / 4.5 s GPU. This blocks a warmed end-to-end
throughput claim. Next work removes redundant cache keys and evaluates shape
bucketing/cache management with memory accounting. It is not continuous admission
or a production serving scheduler yet.

### Bounded Cache Correction

The profile identified eight row counts with roughly 220 packed projection entries
each. The old 1024-entry all-or-nothing eviction repeatedly discarded the working
set. A 4096-entry probe removed all third-run preparation, preserved exact outputs,
and reached 0.72 s CPU / 0.58 s GPU for the four-request workload. Peak RSS was
6.47 GB CPU / 8.15 GB GPU; sampled Metal allocations peaked at 5.02 GB. These are
single-process diagnostics, not a matched performance acceptance result.

The default is now a bounded 4096-entry LRU cache, evicting the least-recent quarter
after a device fence. Parameters are retained per entry, so eviction releases their
owners without dropping hot operators. `KIDI_OPERATOR_CACHE_CAPACITY=1..16384`
provides a bounded override. The existing queued/escaped-output test now crosses
the new limit and verifies a hot operator is retained. The limit counts entries,
not bytes or native-library allocations. Device-embedding batch generation also
matches serial with zero warm preparation. All 16 existing CTest targets pass.

### Incremental Admission Foundation

An owned `GreedyState` centralizes incremental stop/length/score rules and is reused
by the existing batch decoder. `Generator::enqueue`, `step`, and `cancel` now provide
thread-confined continuous admission, stable request IDs, streamed token/completion
events, bounded outstanding requests, and a reserved dense-cache token budget.
Ready rows decode together; one bounded prefill chunk is scheduled per step with
round-robin progress among prefilling rows. Completed/cancelled slots are reclaimed.
Model execution failure invalidates this queue; reload is required, rather than
retrying a possibly partially written state.

A real-checkpoint regression on CPU and GPU matches four serial generations with
heterogeneous limits, including streamed tokens, enqueue during generation, queue
backpressure, and active/waiting cancellation. This is a callable C++ serving core,
not a network service. Active caches remain dense; prefix-cache options are rejected
for queued requests. It does not yet provide direct paged attention, mixed packed
prefill/decode in one model call, speculative decoding, or whole-step replay.

Three fresh processes per backend now measure static four-request generation with
two warmups, three measurements, alternating serial/batch execution order, and
zero preparation in every measured run. Median paired full-request speedup is
1.214x CPU and 1.116x GPU; all outputs and stop lengths agree. Per-process median
times were CPU serial 868/883/876 ms versus batch 716/720/720 ms, and GPU serial
642/638/637 ms versus batch 575/573/571 ms. Raw measurements and binary identity
are in [batch-results.json](batch-results.json). This is not a continuous-admission
latency measurement or a comparison against batch-one LiteRT-LM.

`generate --input-lines FILE` now exposes the validated scheduler for finite prompt
files (or `-` for finite stdin), returning completion-order JSONL with 1-based
request IDs. `--max-active`, `--queue-size`, and `--cache-tokens` bound admission.
A three-prompt/two-slot GPU smoke test produced valid identified results. Cold
preparation dominated that smoke test; its timings are not throughput evidence.

## Direct Paged Attention: Experimental Primitive

Added an explicit decode-only page-bank attention operator: CPU online-softmax
reference and Metal 64-token partitions with stable softmax merge. Dense-oracle
tests cover head widths 40/256/512, GQA, nonsequential physical pages, unequal
77/133 lengths, partial tails, local windows, and invalid page IDs. The pool wrapper
validates initialized prefixes and retains leases through queued reads. A released
request cannot recycle those pages before synchronization.

The initial Metal kernel was slower on most production shapes. Cooperative merge
alone did not fix it. Specializing page/head geometry and sharing page addresses
with vectorized value loads improved four-request short-history and local-window
cases, but global length-4096 still costs roughly 522/1043 us versus dense
324/666 us at widths 256/512. These are isolated host-plus-completion microbenchmarks,
not model speedups. `kidi_metal_packed_bench paged-attention` reproduces the probe.

`KIDI_PAGED_ATTENTION_PROBE=1` views existing dense caches as physical pages without
making a second K/V copy, only for one-token query segments. Tiny original/QAT
fixtures retain the existing tolerance. On the independent full-model 29-position
probe, GPU top-1 remains 29/29 but KL changes 0.0365263 -> 0.0311802 and NLL delta
-0.0057946 -> +0.0298538; CPU top-1 remains 28/29 with changed metrics too. This
does not establish numerical equivalence or broad quality. The probe is OFF by
default, and queued serving still uses dense attention. Direct paged state ownership
in the model, multi-request bank fusion, and a fast global kernel remain unfinished.

## Second Opinion and Priority Reset

User requested a pause to reassess the approach. The strongest evidence favors
removing proven copies, allocations, and repeated preparation while preserving
existing arithmetic. Several custom attention and matmul attempts passed small
tests but lost on real shapes or changed QAT behavior. Repeating that cycle without
better attribution is not an efficient route to leadership. Likewise, batching and
prefix capabilities are useful but do not satisfy the original uncached batch-one
latency target. The feature roadmap is not a performance acceptance checklist.

Priority now returns to the larger prefill gap. Pause new serving features and
attention/replay promotion while collecting a focused prefill cost breakdown.
Distinguish CPU encode/dispatch, actual device work, synchronization, and cold
preparation. Instrumented synchronized timings are diagnostic, not ordinary GPU
kernel timings. Choose the next implementation from a measured dominant cost and
an estimated maximum whole-request benefit, rather than a convenient kernel to
tune. Retain the existing numerical gates and separate workload scoreboards.

The current shared-calibration change is being closed out before that next choice.
One stream-owned rounded input is reused only for identical source/shape/scale and
FP32/FP16 output policy, with ownership and write/fence invalidation. It does not
combine weights or change matmul shape. Three alternating process pairs per case
preserve all 18 measured outputs with zero preparation. Request time improves in
every pair, typically about 1-2%; one short-prompt pair has larger drift and should
not define the claim. This is a bounded optimization, not an answer to the prefill
gap. `KIDI_DISABLE_CALIBRATION_REUSE=1` retains the comparison path.

All 16 tests and the real serving regression pass with shared calibration; both
independent GPU decode and prefill metrics are unchanged. Raw paired results are
in [calibration-results.json](calibration-results.json).

### Evidence-driven Follow-up

A deliberately synchronized 1024-token/chunk-512 prefill trace attributes about
493 ms to packed projections and 112 ms to attention, out of roughly 831 ms of
operator execution/wait time. Synchronization perturbs the workload and disables
cross-operator calibration reuse; these are ranking diagnostics, not ordinary GPU
kernel times. The largest MLP up/down projection shapes dominate.

The native `MPSMatrixMultiplication` alternative supports the same FP16 inputs and
FP32 output and matches MPSGraph exactly on tested matrices. It does not improve
the dominant production shapes: chunk-512 up/down projections remain roughly
1.43/1.79 ms. Physically transposed weights also fail to improve those shapes.
No production backend/layout change was made. The `native-matmul` benchmark records
whole-call timings; graph GPU timestamps are omitted when MPSGraph splits command
buffers, rather than misreporting a partial interval.

Chunk 1024 is not promoted: a current first-output probe is about 621 ms versus
552 ms for chunk 512, with sampled Metal allocations 8.12 versus 6.84 GB. System
swap use grows during the trial, so this is not a clean memory-capacity acceptance
result. Continuing to increase working sets is not the right next step on this
16 GiB machine.

### Bounded Expanded Weights

Added opt-in `KIDI_PREFILL_CACHE_BYTES=N` (0..16 GiB): retain expanded FP16 weights
up to this byte budget and unpack remaining packed matrices on GPU into reusable
scratch. Existing matmul/calibration order is unchanged. The budget covers retained
expanded matrices only, not packed model weights, scratch, native-library memory,
or total RSS. Shared output reuse is required. `KIDI_STREAM_PREFILL_WEIGHTS=1` is a
zero-retention experiment and cannot be combined with the byte-budget override.
The default retains the previous all-weight cache policy.

Initial long-prompt/chunk-512 probes preserve exact generated tokens, zero warm
preparation, and unchanged independent 128-position reference metrics. Zero retained
weights gives about 1574 prefill tokens/s and 3.68 GB sampled Metal allocation;
a 1 GiB budget gives 1656 tokens/s and 4.38 GB, versus roughly 1830-1870 tokens/s
with all matrices retained. Decode stays near 84.5 tokens/s. These single-process
probes show a memory/latency tradeoff, not a new speed result. Mixed cached/streamed
execution passes the existing eager/model tests with a deliberately tiny budget.

## Root Cause Found: Excess Prefill Computation

The second opinion ultimately changed the problem, not just the kernel choice.
Direct inspection of the shipped LiteRT FlatBuffer found 35 attention blocks and
277 fully connected operators in decode, but only 14 attention blocks and 129
fully connected operators in both prefill signatures. Gemma E2B's final 20 layers
reuse earlier K/V. For cache-only prompt tokens, those consumer layers have no
retained output. Kidi had still been evaluating all 35 layers.

Cache-only prefill now runs through the last K/V producer and stops immediately
after that producer's K/V projections, normalization/calibration and writes.
It skips the last producer's unused query/attention/MLP and all shared consumers.
Requested all-token logits remain on the complete model path. No model equations,
trained scales, cache layout, or numerical tolerances change. Existing model tests
now additionally require byte-identical K/V versus complete evaluation of the same
prefix. Default and device-state paths pass.

Three fresh before/after/LiteRT processes per backend, two warmups and three
measurements, 1024 prompt tokens, chunk 128, 64 recurrent outputs:

- CPU prefill: before 471-494, pruned 1129-1218, LiteRT 555-589 tokens/s.
- GPU prefill: before 1431-1442, pruned 3336-3394, LiteRT 2617-2625 tokens/s.
- All 18 measured candidate generations equal the frozen baseline; warm
  preparation is zero. Decode does not materially change; GPU still trails LiteRT.

This is a long-prompt prefill result, not overall industry leadership. Phase and
precision caveats remain. It also corrects the earlier interpretation of the gap:
profiles of unnecessary work can send optimization toward the wrong abstraction.
Compare operation counts and required retained state before tuning microkernels.

## Preserve Producers, Trim Shared Consumers

Further diagnostics separated two algorithms. Splitting input into prefix plus
four-token tail preserved short outputs but consistently changed the long prompt
at generated token 2; it is OFF by default (`KIDI_MULTIROW_PREFILL_TAIL=1` for the
experiment). Simply forcing scalar FP16 projections also failed and was removed.

The accepted native-QAT Metal policy evaluates the full projected chunk through
all K/V producers, then slices only the shared consumer layers' query activations,
PLE, masks and RoPE to four rows. No producer/cache computation changes. It applies
to chunks >=64, not all-token logits or packed-only prefill. The opt-out is
`KIDI_SHARED_PREFILL_TAIL=0`; `shared_prefill_tail` records the policy. Long
259/1027-token fixtures additionally compare against complete all-logit evaluation.
All 18 paired timing-case continuations and six varied text/reasoning/code prompts
are exact; serving/prefix reuse regressions pass. This is not universal bitwise
logit equality: 128 independent fresh-prefix endpoints retain 123/128 top-1, but
KL changes 0.0137343 -> 0.0143124 and NLL delta -0.0204503 -> -0.00614065.
