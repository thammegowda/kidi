# Gemma 4 E4B: Kidi vs. vLLM vs. llama.cpp, Q8 on H100

## Current state: November 22 — Hopper FA3 removed

Removed the Hopper-only attention kernel and its build/dispatch wiring. FA2
now handles eligible BF16-cache prefill. The older tiled BF16 kernel is
still used for short queries, arbitrary masks and devices that cannot
allocate enough shared memory for FA2. FP32-cache, decode and generic
fallback routes are unchanged. The SM90 W8A8 GEMM stays.

Consolidating BF16 head-width dispatch and deleting the unreachable SiLU gate
branch from the generic pointwise kernel brings the total to 479 fewer
CUDA source lines. SiLU gates still use the dedicated activation kernel.
The release benchmark executable shrank from 17,917,472 to 17,692,168 bytes
(1.3%). Both CUDA tests pass.

## November 22 — residual and decode simplification

Removed the experimental two-output residual projection prologue. Gemma again
runs post-attention RMS norm + residual add as one op, then fuses the pre-FFN
RMS norm into gate/up quantization. This removes the special dispatch key,
second projection output, and plumbing through the model and operator runtime.
Decode attention now directly implements one query head per CTA; its unused
two-head alternative was unreachable. The 16-/32-key partition policy stays.
Together these delete 124 production lines and 84 experiment-specific test
lines. The release benchmark executable shrank from 18,753,056 to 17,917,472
bytes (4.5%).

five translations and chrF 57.30 were unchanged. This measured the cost
of removing FA3; the kernel was still present in this snapshot.

For a larger cleanup, consolidate the two portable BF16 prefill attention
kernels, rather than deleting reachable fallbacks. FA2 handles large
unmasked or broadcast-causal workloads; the older tiled kernel
handles short queries and arbitrary additive/non-broadcast masks. Any
replacement must cover both, with performance checks on Ampere as well as
Hopper. Keep the separate decode kernel and generic attention fallback.
Likewise, KV-state retirement protects pending device readbacks; it is not
redundant with the idle-state pool and should not be removed to simplify
generator ownership.

## November 22 — residual + next norm experiment (removed)

The attention-to-FFN boundary now fuses
`post_attention RMS norm → residual add → pre_ff RMS norm → int8 quantization`
inside the gate/up projection prologue. It returns two outputs: the
input-shaped F32 residual sum (needed by the next skip connection) and the
gate/up projection. The normalized FFN input stays in registers; there is no
extra F32 intermediate or quantize/dequantize chain.

This reuses the projection prologue and existing paired-output/replay machinery,
not prefill graph capture. The residual is a dynamic operand, excluded from
constant-parameter cache keys and retention. Both RMS reductions and the
contracted post-norm residual add match the existing CUDA arithmetic bit-for-bit.
The fused path is CUDA checkpoint-precision F32 W8A8 per-channel prefill, with
at least 32 rows and width at most 2560. Decode, BF16, other precisions/backends,
grouped/zero-point weights and wider rows retain the decomposed path.

An initial two-output norm kernel materialized the normalized input and
required separate quantization. Its p2048 TTFT was 42.56 ms, so that prototype
was removed in favor of the integrated quantization island.

## November 22 — norm/activation/quantization islands

Following Tahoma's `rms_norm_int8` recipe, CUDA prefill now fuses each
normalization or gate into the activation quantization of the projection it
feeds. A `PACKED_LINEAR` carries an optional prologue (`ProjectionPrologue`):
RMS norm for `input_norm → q/kv` and `pre_ff → gate_up`, and the GELU gate for
`gate_up → down`. The normalized or gated F32 activations are never written;
the prologue kernel holds a row in registers and emits int8 values plus
per-row scale/zero for the W8A8 GEMM. Head-wise q/k RMS + rotary now runs one
warp per 256/512-wide head row instead of one under-filled 256-thread block.
Both kernels replay the unfused arithmetic and reduction order, so outputs are
bit-identical. Fusion is limited to F32 W8A8 per-channel inputs with at least
32 rows; decode and other backends run the prologue as a separate operation.

Quick run (`--label norm-quant-fusion`): all 128 tokens per speed prompt and
all five translations match the saved Kidi baseline.

### KV-cache allocation

`Generator::warm_up(chunk, context)` now preallocates one full-context Gemma
CUDA state. Completed text-only states are rewound and kept in a pool bounded
by the serving active-request limit and cache-token budget. Eager and serving
generation both acquire matching-capacity states; a changed capacity replaces
unmatched idle states. Reuse does not report or retain a prompt prefix.
Multimodal/speculative states are excluded.

States with pending decode readbacks stay retired until the last readback is
ready, then rewind synchronizes device work before reuse. Unused cache contents
need not be cleared: prefill overwrites every visible position and attention
masks out unwritten positions. `memory().cache_bytes` includes idle cached
states, and `release_workspaces()` releases the pool.

nsys confirmed measured admission dropped from **49 `cudaMalloc` calls to 2**:
the 48 per-layer K/V allocations and cache-clearing memsets no longer recur.
The two remaining calls are small non-cache allocations, not a claim of a
globally allocation-free runtime.

Validation: CUDA runtime/operator and Gemma/model/speculative tests passed,
as did the CPU model tests. Isolated FA3 tests passed Compute Sanitizer
memcheck and racecheck (zero errors/hazards), including F32/BF16 I/O, D256/D512,
batched/non-power-of-two GQA, key offsets, partial tiles and fully masked rows.
The unfiltered memcheck also exposed an out-of-bounds shared-memory read in
the unchanged `parallel_attention<BF16,32,BF16>` path; that separate issue
was not changed here.

### Remaining speed work

- Fuse residual + RMSNorm + per-token int8 quantization, and GELU·mul +
  quantization, so GEMMs read int8 activations directly
  (`quantize_rows`, `gated_activation`, `dense_rms_normalize`, about 18 ms;
  largely done in the norm/activation/quantization section above).
- Any further attention changes should beat the remaining 2.39 vs. 1.58 ms
  gap without sacrificing the compact implementation or output quality.
- Close the decode gap of about 165 vs. 193 tokens/s.

## Precision: what actually ran

| Engine | Linear projections | Embeddings / tied output head | KV cache |
|---|---|---|---|
| Kidi | Per-output-channel INT8 weights; dynamic asymmetric per-token INT8 activations | Q8 | FP32 |
| vLLM | The same INT8 linear matrices/scales as Kidi; dynamic symmetric per-token INT8 activations | Original BF16 | BF16 |
| llama.cpp | Q8_0 blockwise weights converted from the same BF16 checkpoint; Q8_1 activation dot/MMQ kernels | GGUF converter's native tensor policy | BF16 |

Kidi's checkpoint is a post-training INT8 export, not the official mixed-bit
mobile QAT checkpoint. Three rows of each of its 379 quantized linear matrices
were reproduced exactly from the pinned BF16 source using the repository's
existing INT8 packer. vLLM reuses those matrices and scales rather than
independently requantizing the linear weights.

Kidi's explicit `--precision w8a8` override currently rejects CUDA. The supported
native packed checkpoint path nevertheless performs INT8 weight/activation
computation: a separate Nsight run observed `quantize_rows`,
`pipelined_w8a8_gemm`, and `quantized_vector_fast`. The vector kernel uses INT8
DP4A instructions. No CPU fallback or BF16 substitution was used for these
packed linear projections.

vLLM explicitly selected `CutlassInt8ScaledMMLinearKernel` for
`CompressedTensorsW8A8Int8`. A separate llama.cpp Nsight run observed Q8_1
activation quantization and Q8_0 vector/MMQ kernels. Profiler runs were not
included in timing measurements. Attention, normalization, and other
non-quantized operations retain each runtime's floating-point implementation.

## Limitations

- Quantization granularity, activation symmetry, embedding/output-head
  precision, and KV/attention precision are not identical. In particular,
  Kidi's FP32 cache differs from the BF16 caches in the other engines.
- All requests returned the required token counts and non-degenerate text.
  This is a latency/throughput benchmark, **not an accuracy evaluation**;
  outputs differ across engines.
- Greedy outputs repeated within each process. Kidi and llama.cpp also
  reproduced output IDs across process runs; vLLM did not. Its decode throughput
  shifted by about 6% between runs, versus about 1% or less for the other engines'
  per-workload medians. Both runs are included rather than selecting the faster
  vLLM result. The decode ranking is unchanged in either run.
- Three prompt lengths, one model, and batch one do not establish concurrent
  serving throughput or general performance across models/hardware.

## BF16-cache optimization follow-up

The uncommitted follow-up on the same parent commit enables AUTO/explicit BF16
cache for native CUDA Q8 checkpoints without replacing W8A8 projections with
BF16 linears. Checkpoint-provided byte-cache policies and CPU defaults are
unchanged; explicit FP32 remains available.

Optimized results pool ten measured requests per workload from two independent
process runs, each with two warm-ups and five measured requests. A fresh
FP32-cache baseline uses five measured requests per workload. All use the
original exact prompt IDs, 128 output tokens, and physical GPU 7 only.
Other engines were not remeasured; their results above remain historical.

| Prompt tokens | Matched FP32 TTFT (ms) | Optimized BF16 TTFT (ms) | Optimized prefill (tokens/s) | Matched FP32 decode (tokens/s) | Optimized BF16 decode (tokens/s) |
|---:|---:|---:|---:|---:|---:|
| 128 | 19.58 | 18.70 | 6,847 | 144.75 | 146.62 |
| 512 | 44.42 | 36.95 | 13,856 | 143.59 | 145.22 |
| 2,048 | 223.06 | 121.05 | 16,919 | 142.29 | 144.15 |

At 2,048 tokens, TTFT decreases **45.7%** and prefill throughput increases
**1.84x**. Decode improves only **1.1-1.3%** across these workloads. KV storage
uses half as many bytes; total peak GPU allocations decrease by approximately
0.65 GiB, not by half, because weights and graph intermediates dominate.
At 128 tokens, total peak allocations are 9,336,270,792 bytes versus
10,040,127,432 bytes in the matched FP32 run.

Measured changes:

- FP32 queries and BF16 K/V are consumed directly by CUDA attention, with FP32
  outputs. Tensor-core prefill rounds queries to BF16 inside the kernel;
  decode preserves FP32 query arithmetic. Separate query/output casts disappear.
- Captured decode scatter converts FP32 updates to BF16 in the cache-write
  kernel. Existing duplicate-index last-write-wins behavior is retained.
- The initial large W8A8 prefill tile was 128x64 for at least 1,024 rows. The
  follow-up tile tuning below supersedes that configuration for long prefill;
  the 128x64 result remains the historical baseline.
- W8A8 decode uses one column per warp below 32,768 output columns. The
  vocabulary projection retains the wide vector kernel.
- Captured-step keys include cache dtype, preventing incompatible FP32/BF16
  replay reuse.

A separate profiled 2,048-token prefill plus seven decode intervals confirms
277 W8A8 GEMM launches and 1,779 INT8 vector launches. Pointwise launches drop
from 1,416 to 408 compared with the initial BF16 implementation; cache scatter
remains 336 launches. Profiler measurements are excluded from the table.

**This does not make Kidi the fastest engine.** Historical vLLM decode remains
about 199-201 tokens/s, and its long-prompt TTFT remains substantially lower.
The final profile still spends 37.0% of GPU kernel time in INT8 prefill GEMM,
16.7% in BF16 FlashAttention, 12.5% in INT8 vector projections, and 6.7% in
activation quantization. These are remaining bottlenecks, not eliminated costs.

Validation: `make test` passed 46/46 and `make test-cuda` passed 47/47.
Focused tests cover mixed attention prefill/decode, masks, cache offsets, GQA,
BF16 scatter rounding/duplicate indices, tiled projection tails, and Gemma
cache precision across prefill, decode, fork, rewind, and graph replay.
All ten real-model requests per workload returned identical greedy IDs within
the BF16 runs and the required token counts. Fixture logits remain finite and
within the FP32-reference tolerance. This is not a model accuracy evaluation;
BF16 rounding can change outputs relative to FP32 cache.

  compiled execution, CUDA graphs, and scheduling settings remain enabled.
  The initial default-fork attempt generated no trace and is not used.
- Additional whole-graph traces at 128 prompt tokens check GPU idle time and

### Decode: the main gap is GPU execution, not host starvation

Summed graph-node-profiled GPU kernel time divided by 127 decode steps:

| Operation group | Kidi ms/token | vLLM ms/token | Kidi/vLLM |
|---|---:|---:|---:|
| Norm, activation, elementwise, activation quantization | 2.354 | 1.181 | 1.99x |
| Attention, including partition merge | 1.372 | 0.512 | 2.68x |
| INT8 linear projections, excluding vocabulary head | 2.294 | 2.556 | 0.90x |
| KV writes | 0.112 | 0.050 | 2.26x |
| Vocabulary head / Kidi greedy selection | 0.247 | 0.465 | 0.53x |
| Other | 0.008 | 0.055 | 0.15x |
| **All kernels** | **6.386** | **4.819** | **1.33x** |

Operation groups are broad: vLLM's Triton kernels fuse multiple operations,
and some of its sampling work falls in Other. Kidi's Q8 head and vLLM's BF16
head are different precision implementations. At 2,048 prompt tokens,
Kidi/vLLM attention grows to 1.489/0.548 ms/token; the other groups remain
similar.

The norm/activation/quantization and attention groups account for approximately
**2.03 ms/token of extra Kidi GPU work** at 128 prompt tokens. Faster Kidi
projections and its Q8 head offset part of this cost. Launch count alone is
not the explanation: Kidi has 1,033 kernels/token versus approximately 935,
only 10.5% more, while total kernel time is 32.5% higher.

Whole-graph traces, counting the union of graphs, eager kernels, copies, and
memsets between the first decode graph and the final GPU activity, show
**99.44% GPU-active for Kidi and 99.37% for vLLM**. Both already launch
127 CUDA graphs. Kidi's graph GPU duration averages 6.777 ms, versus
4.608 ms for vLLM, but vLLM executes its vocabulary head outside the graph.
Thus the 0.562 ms between vLLM graphs is not pure CPU idle time.
Kidi's corresponding interval averages 0.059 ms.

Graph-node tracing inflated summed Kidi `cudaGraphLaunch` API time to
786.7 ms, versus 15.3 ms in the whole-graph trace. This is profiler overhead,
not evidence that graph submission is the root cause. Similarly, a Kidi
4-byte first-token D2H API call waited 88.1 ms during long prefill; that is
waiting for prior GPU work, not 88.1 ms of transfer work.

### Prefill: GEMM and attention need separate fixes

Summed GPU kernel time before the first decode graph, 2,048 prompt tokens:

| Operation group | Kidi ms | vLLM ms | Kidi/vLLM |
|---|---:|---:|---:|
| INT8 projections | 52.816 | 13.586 | 3.89x |
| Attention | 23.922 | 1.571 | 15.23x |
| Norm, activation, elementwise, activation quantization | 20.486 | 6.457 | 3.17x |
| **All kernels** | **97.761** | **22.455** | **4.35x** |

Projection and attention groups account for 52.1% and 29.7% of excess
prefill kernel time respectively. Kidi launches 277 prefill INT8 projections
versus 253 in vLLM. Its graph projection merger is single-row-only
(`activation.numel() == width` in
[operators.cpp](../../kidi-ops/src/cuda/operators.cpp)); vLLM packs QKV for
the 24 KV-producing layers in both phases. Decode already has 253 projections
in both engines, so adding decode QKV packing again is not the priority.

### Hardware counters and source-backed causes

Representative Nsight Compute results:

| Kernel | Kidi | vLLM |
|---|---|---|
| First D256 decode attention | 38.05 us; 16 CTAs; 1.58% SM throughput | 12.35 us; 128 CTAs; 19.09% SM throughput |
| Single-row residual RMSNorm / vLLM fused residual-norm-quantization | 8.00 us; one CTA | 6.82 us; one CTA |
| First prefill INT8 projection, M=2048, K=2560, N=10752 | 439.01 us; 46.86% SM throughput | 94.69 us; 79.44% SM throughput |

Counter times are isolated replays and differ from Nsight Systems kernel
times. The norm rows do different fused work; the GEMM dimensions and INT8
weight shapes were checked against both checkpoints.

Concrete optimization priorities:

1. **Fuse decode normalization/activation with quantization and adjacent
   residual/scale operations.** Kidi's group has 643 kernels/token versus
   555 for vLLM and costs twice as much. Its generic RMSNorm kernels use
   one 256-thread CTA per row, cross-warp reductions, and two block barriers.
   vLLM's observed kernels fuse residual/RMSNorm/quantization and
   GELU/multiply/quantization. Reuse the same principle that helped Tahoma;
   preserve Kidi's quantization rounding rather than silently switching precision.
2. **Continue specializing decode attention.** A one-query-head-per-CTA
   schedule doubled Kidi's short-prompt D256 grid from 16 to 32 CTAs and
   improved full decode throughput by 1.95-2.27%. The active vLLM SM90
   FlashAttention kernel launches 128 CTAs and remains substantially better
   utilized. Kidi's D512 partition kernel also uses 148 registers/thread in
   the Systems trace. A measured 32-key schedule adds 1.69% decode throughput
   for contexts of at least 2,048 keys; shorter contexts retain 16-key
   partitions. BF16 cache storage alone did not fix attention execution.
3. **Continue tuning the SM90 INT8 prefill GEMM.** A corrected matched
   comparison retained 128x128 over 64x256. Earlier claims that 64x128
   beat 128x128 were invalid because the 128x128 launch grid was oversized.
   W8A8 remains a large profiled cost and is not yet competitive with vLLM's
   persistent TMA warp-specialized CUTLASS kernel.
4. **Further specialize causal/windowed prefill attention.** Compact
   query-position metadata removes dense CUDA host masks. The selected kernel
   now skips mask loads and synchronization for fully valid causal and
   windowed tiles, with identical generated tokens.
   The original profile still showed a 15.2x attention-group gap; an efficient
   causal/window-specialized launch schedule remains open.
5. **Remove request-time allocation and intermediate materialization.** Even the warmed
   Kidi request performs 57 `cudaMalloc` and 57 `cudaFree` calls; vLLM performs
   none. The baseline 2,048-token trace transferred 39.9 MB H2D, including
   two 16 MiB FP32 attention masks; those masks are now represented by query
   positions and key bounds on CUDA. Kidi also copies 440.4 MB D2D in 147
   prefill copies. Reuse workspaces and avoid materializing strided
   intermediate views where the consumer can read them directly.
6. **Reduce replay staging traffic.** K/V writes now fuse to 24 decode scatter
   kernels per token, matching vLLM's count; the broader graph still stages
   buffers and performs many prefill copies.

These priorities came from measured profiles. Adaptive decode partitioning
and compact CUDA causal-mask representation are verified improvements; the
remaining items still require implementation and end-to-end measurement.
Reaching vLLM's norm/activation and attention costs would remove roughly
2 ms/token of GPU work.

## Compact CUDA causal masks

Gemma 4 CUDA attention now passes compact I32 query positions to the CUDA
attention kernels, which apply causal and sliding-window bounds in-kernel.
This removes the two dense 16 MiB FP32 mask allocations/transfers from the
2,048-token prefill path. Other backends retain their additive F32 mask path.
Focused CUDA tests compare compact causal and sliding-window attention against
the dense-mask reference across prefill rows; the full CUDA suite passes 47/47.

The GPU-7 measurement used BF16 KV cache, identical Gemma 4 E4B Q8 prompts,
128 generated tokens, and five measured requests per process. The restored
dense-mask baseline is one five-request run; the structured-mask candidate
median is across three five-request runs. GPU clocks were unlocked and the host
is shared.

| Prompt tokens | Dense-mask TTFT (ms) | Structured-mask TTFT (ms) | Dense prefill (tok/s) | Structured prefill (tok/s) | Structured decode (tok/s) |
|---:|---:|---:|---:|---:|---:|
| 128 | 18.50 | 18.18 | 6,920 | 7,039 | 166.56 |
| 512 | 37.32 | 36.51 | 13,720 | 14,022 | 161.81 |
| 2,048 | 122.44 | 106.80 | 16,727 | 19,176 | 156.13 |

At 2,048 tokens, TTFT improves 12.8% and prefill-through-first-token
throughput improves 14.6%. Measured peak GPU allocation falls by 33.6 MB.
Decode is effectively unchanged. Requests were deterministic and returned
the expected token count. This is a Kidi before/after result, not a new
three-engine comparison: the historical vLLM and llama.cpp long-prompt TTFTs
remain 28.20 ms and 101.38 ms, respectively. Kidi is still behind both in
long-prompt TTFT and remains behind the historical vLLM decode result.

The mask-transfer milestone is complete, but attention remains a major
bottleneck. FlashAttention now bounds each query tile's key loop using the
minimum and maximum query positions: causal attention stops after the latest
query position, while windowed attention also starts at the earliest visible
key. This path is used for multi-query calls with more than 512 keys, avoiding
its setup and synchronization cost on short prompts and decode.

On physical GPU 7, four candidate process runs (five measured requests each)
gave median 2,048-token TTFT of 101.53 ms and prefill throughput of 20,171
tokens/s, versus 106.80 ms and 19,176 tokens/s for the compact-mask-only
candidate. That is a 4.9% TTFT reduction and 5.2% prefill-throughput gain;
decode remained effectively unchanged at 156.85 versus 156.13 tokens/s.
Requests were deterministic and peak GPU allocation was unchanged. Smaller
prompt measurements did not show a consistent change. This remains a Kidi
before/after measurement, not a fresh comparison against vLLM or llama.cpp.

This bounds unnecessary key-tile traversal but does not close the profiled
attention gap. The SM90 INT8 prefill GEMM, more efficient attention scheduling,
runtime allocation/copy overhead, and decode norm/activation work remain open.

## Unique-index cache scatter

Captured Gemma 4 CUDA steps generate cache indices as `position + query`, so
their write positions are unique. These writes now use a CUDA-only scatter
path that skips duplicate-index arbitration; generic scatter retains its
existing last-write-wins behavior. A focused test covers both the unique path
and duplicate indices.

On GPU 7, two 2,048-token candidate runs (five measured requests each) gave
median TTFT of 100.99 ms and prefill throughput of 20,279 tokens/s, compared
with 101.53 ms and 20,171 tokens/s for the key-range-only build. This is about
a 0.5% improvement, with unchanged decode throughput. The profile contains 336
scatter launches totaling 0.80 ms (0.6% of profiled GPU kernel time), so this
is a verified but small end-to-end optimization. This first change left the
separate K/V writes intact; the subsequent section measures their fusion.

## Structured causal prefill tile fast path

For structured causal masks with no sliding window, key tiles ending at or
before the minimum query position are fully valid for every query in the CTA.
The BF16-cache and FP32-cache FlashAttention kernels bypass per-element
mask reads and mask-related block synchronizations for those tiles. Diagonal
tiles and arbitrary masks retain the existing checks. The
partial-tile bound comes from the same structured query-position metadata as
the key-range calculation.

Three GPU-7 processes with five measured 2,048-token requests each showed a
1.64% prefill-through-first-token throughput increase and 1.62% lower TTFT.
Decode was unchanged within run variation, and all 128 generated token IDs
matched the adaptive-partition baseline exactly.

Nsight Systems `cuda_gpu_kern_sum` independently showed total prefill
FlashAttention kernel time falling from 11.71 ms to 10.51 ms (-10.24%) across
the 2,048-token profile. The D512 kernel decreased from 5.53 ms to 4.34 ms;
the D256 kernel remained about 6.18 ms. These are profiled diagnostics, not
throughput measurements.

| Configuration | TTFT (ms) | Prefill (tokens/s) | Decode (tokens/s) |
|---|---:|---:|---:|
| Adaptive partition baseline | 100.22 | 20,436 | 164.44 |
| Fully valid causal-tile fast path | 98.60 | 20,772 | 164.65 |

The same optimization was extended to sliding windows: a tile is skipped only
when it lies within the window of every query in the CTA. Two interleaved
GPU-7 rounds, each with three processes per variant and five requests per
process, measured prefill gains of 1.55% and 0.29% at 2,048 tokens. Separate
Nsight traces measured the 35 D256 attention launches at 6.17 ms versus
4.94 ms; unlocked clocks limit comparison. All 60 output sequences matched;
CUDA parity tests cover non-monotone positions, one-token windows, and FP32
cropped caches. Low-level position masks may also vary by head or key;
the shared-tile bounds and fast path are restricted to masks broadcast along
both dimensions. FP32 and BF16 cache tests cover those non-broadcast cases.

## Rejected multi-row prefill projection fusion

I extended graph projection merging to multi-row W8A8 and split the combined
result into the original outputs with 2D device copies. Single-row and
three-row CUDA parity tests passed, but three GPU-7 process runs did not show
an end-to-end gain. At 2,048 prompt tokens, the candidate median was 100.60 ms
TTFT and 20,357 prefill tokens/s, versus 100.14 ms and 20,452 tokens/s for the
128x128 W8A8 build; decode was effectively unchanged. The trial was reverted
rather than retain the extra copy path without a measurable improvement.

[optimization journal](../../../tahoma/notes/gemma4-moe-optimization-journal.md)
records the same successful pattern: removing routing D2H synchronization,
fusing norm/quantization and activation/quantization, and measuring whole-path
effects. Its first projection-only QKV packing attempt regressed 30% because
strided-view materialization erased the GEMM savings. Avoid repeating that
mistake in Kidi.

With the prepared local environments, binaries, and model artifacts:

```bash
export CUDA_VISIBLE_DEVICES=7
PYTHON=.cache/x64-gemma-venv/bin/python
DRIVER=.cache/benchmarks/e4b-q8-gpu7/run.py

"$PYTHON" "$DRIVER" vllm
"$PYTHON" "$DRIVER" llamacpp
"$PYTHON" "$DRIVER" kidi
"$PYTHON" "$DRIVER" summarize
```

The final command validates and pools the new measurements with the retained
first round. Preserve or replace that first-round dataset explicitly before
using this local driver for a different experiment.
